# ADR 001: Джерела даних для результатів гонки (мультиплеєр)

## Контекст

Фронтенд очікує в `simulationResult` секторні часи по колах, heatmap кольорів по **кожному** сектору окремо та таймлайн подій. Потрібно вирішити, звідки беруться ці дані для user-vs-user матчу з власним `simulationSeed`.

## Варіанти

### 1. OpenF1 (відкриті дані реальних сесій)

- **Що дає:** інтервали, секторні спліти, події для **реальних** гонок; зручно для порівнянь з реальним ГП.
- **Обмеження:** немає «нашої» симуляції; rate limits; дані лише для історичних сесій; не можна підставити часи гравців як ground truth без окремого продуктового режиму «replay vs real», інакше це підміна результату матчу.

### 2. Jolpica / Ergast-спадщина

- **Що дає:** підсумки чемпіонатів, результати заїздів, інколи найшвидкі кола.
- **Обмеження:** агрегати, **немає** повної телеметрії «кожне коло × три сектори» для довільного матчу; погано лягає на heatmap і синхронний таймлайн двох гравців.

### 3. Чисто симуляційний шлях (обрано для MVP)

- **Що дає:** `SimulationEngine` уже емітує `sectorSplits`, події (піт, lock-up, safety car, тощо) детерміністично від `seed` + `sessionId` (salt). Два прогони з однаковим `simulationSeed` і різними telemetry session id дають узгоджений shared RNG для спільних подій і окремі car streams.
- **Чому MVP:** повний контроль контракту API, відтворюваність, немає залежності від зовнішнього API в гарячому шляху матчу.

### 4. Гібрид

- Симуляція лишається **єдиним джерелом правди** для часів і класифікації heatmap.
- Опційно пізніше: текстові «flavor» події або підказки з OpenF1 для того ж треку/року **лише як косметика**, з явним прапором режиму в API, без підміни числових результатів гравців.

## Рішення

- **MVP:** варіант 3 — усі `laps[].sectors`, `sectorHeatmap`, `events` (включно з синтетичними `LEAD_CHANGE` від сукупного часу) будуються з **результату симуляції** та зберігаються в `Lobby.simulationResult` з `schemaVersion: 2`.
- **Пізніше:** гібрид (4) за окремим endpoint / `mode=flavor`, заборона змішувати з основним матчем без явної згоди в контракті.

## Наслідки

- OpenF1 / Jolpica залишаються корисними для **інших** фіч (калібровка, копірайт, порівняння з реалом), не для запису офіційного результат матчу користувача.
- Класифікація heatmap **завжди** по трьох незалежних рядах S1–S3; контракт задокументований у JSDoc `buildSectorHeatmap`.
