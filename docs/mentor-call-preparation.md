# Підготовка до дзвінка з ментором (F1 Gambit API)

Короткий конспект: **що таке технології/підходи**, **навіщо вони потрібні**, **де саме в проєкті** і **що розповісти усно**. Можеш читати з екрана під час розмови.

---

## Як представити задачу одним абзацом

На бекенді (NestJS + TypeORM + PostgreSQL) для мультиплеєру в лобі потрібно було зменшити **гонки (race conditions)** і **неузгодженість даних**, коли два запити робляться одночасно або симуляція вже закінчилась, а запис у БД падає. Додано **атомарні оновлення** при join, **транзакцію після симуляції** (телеметрія + Elo + фініш лобі одним блоком), **фільтр для помилок БД**, **middleware** для логування та correlation id, **доменні події** після ключових кроків, і **зафіксовано політику версіонування API** (`/api/v1` + `schemaVersion` у JSON).

Ключові файли:

| Тема | Де подивитися |
|------|----------------|
| Join + optimistic update | `src/modules/lobby/lobby.service.ts` → `join` |
| TX після симуляції | `src/modules/lobby/lobby.service.ts` → `startSimulation` |
| Рейтинг у транзакції | `src/modules/users/rating.service.ts` → `processResultInTransaction` |
| Події лобі | `src/modules/lobby/events/lobby.events.ts`, `lobby-events.listener.ts`, емісія в `LobbyService` |
| Помилки PG | `src/common/filters/query-failed.filter.ts` |
| HTTP access + request id | `src/common/middleware/http-access-log.middleware.ts`, `src/common/http/request-id.util.ts` |
| Префікс API + текст для Swagger | `src/common/api-versioning.ts`, `configure-app.ts`, `lambda.ts` |

## 1. Транзакції в БД (TypeORM)

### Що це таке простими словами

**Транзакція** — це набір операцій до БД, які або **всі виконуються**, або **всі скасовуються (rollback)**. Проміжний стан іншим підключенням не видно (на рівні ізоляції, який дає Postgres).

### Навіщо у веб-api

Якщо зробити крок А (оновити рейтинг) і крок Б (записати результат у лобі) **окремими комітами**, при падінні між ними база буде «напів правдива»: наприклад, рейтинг змінився, а `FINISHED` і `simulationResult` не збереглися.

### Як застосовано тут

- **Симуляція (`runMultiplayer`) тримають поза транзакцією** — це довгі CPU-кроки, небажано блокувати конекшн до БД.
- **Після успішної симуляції** відкривається **одна транзакція** (`EntityManager.transaction`): запис телеметрії, підрахунок і збереження Elo через той самий `manager`, оновлення лобі `FINISHED` + `winnerUserId` + `simulationResult`. При будь-якій помилці — rollback усього блоку; у `catch` статус лобі відкочується на `CONFIGURING` (як і раніше логіка «не залишаємо в неконсистентному SIMULATING» без повного результату).

- **`RatingService`**: основна логіка винесена в приватний `processResultWithManager`; публічний **`processResultInTransaction(manager, …)`** дозволяє викликати оновлення рейтингу **усередині чужої транзакції** (з `LobbyService`).

Фраза для ментора: *«Я не об’єдную важкий CPU і транзакцію; транзакція стисла і тільки для узгодженого запису після результату симуляції.»*

## 2. Атомарний `join` (умовний UPDATE)

### Що проблеми без цього

Два користувачі одночасно читають «лобі чекає, опонента нема», обидва проходять перевірку `opponentUserId == null`, обидва намагаються записати — можливий **lost update** або дивна поведінка.

### Що зробили

Замість «прочитав → перевірив → save» використовують **`update` з умовою в `where`**: тільки рядки в статусі `WAITING` з `opponent_user_id IS NULL`. Якщо `affected === 0` — хтось уже зайняв слот → **`409 Conflict`** з зрозумілим текстом.

Це **оптимістичний/умовний** підхід (без явного `SELECT … FOR UPDATE` у цьому місці).

Фраза: *«Join робиться одним умовним UPDATE; при гонці клієнт отримує Conflict замість некоректного стану.»*

## 3. Middleware (Express / Nest на рівні пайплайна)

### Що це

**Middleware** — функція «на вході» HTTP: виконується для запитів **до** більшості логіки контролерів/guards (залежно від порядку підключення). Тут він глобальний у `configure-app`/`lambda`.

### Навіщо

- Стабільний **`requestId`** на об’єкті запиту (з заголовка `X-Correlation-Id` / `X-Request-Id` або новий UUID) — одна й та сама ідентифікація видна у фільтрах, інтерцепторі, логах.
- **`requestStartedAt`** для обчислення тривалості.
- **Один рядок access-log** при `res.on('finish')` — зручно дебажити і моніторити без розмазування по коду.

Фраза: *«Correlation id раніше з’являвся в інтерцепторі; middleware виставляє id ще до відповіді, щоб фільтри помилок теж могли його логувати.»*

## 4. Exception filters (глобальна обробка помилок)

### Що це у NestJS

**Filter** ловить виняток і формує **HTTP-відповідь** замість падіння в сирий стек 500 там, де можна трактувати помилку предметно.

### Що вже було

Глобальний **`HttpExceptionFilter`** формує узгоджений JSON: `success: false`, `statusCode`, `error`, `requestId`, тощо.

### Що додано (PostgreSQL через TypeORM)

**`QueryFailedFilter`** для `QueryFailedError`: типові коди Postgres — **`23505` (unique)** → **409** з `code: 'UNIQUE_VIOLATION'`, **`23503` (foreign key)** → **400** з `code: 'FOREIGN_KEY_VIOLATION'`. Інші — як раніше 500 із логом. У не-production часто доклеюють `detail`/`constraint` для дебагу.

### Порядок реєстрації

Специфічніші фільтри зазвичай реєструють **перед** загальним catch-all (тут спочатку `QueryFailedFilter`, потім `HttpExceptionFilter`).

Фраза: *«Клієнт отримує передбачувані коди для типових помилок інтеграції з БД, а не голий 500.»*

## 5. Події (EventEmitter у NestJS)

### Що це

Внутрішній **publish-subscribe**: сервіс **емітує** подію, інші класи (**listeners**) підписані через `@OnEvent`. Це **не** REST і **не** WebSocket для браузера — це зв’язок **в межах процесу** бекенду.

### Навіщо

Розвантажувати `LobbyService`: після ключової бізнес-дії не треба в одному методі смикати аудит, метрики, майбутній broadcast — можна почати з **тонких listener’ів**.

### Як саме тут

- **`LOBBY_OPPONENT_JOINED`** — після успішного збереження join.
- **`LOBBY_BATTLE_FINISHED`** — **після коміту** пост-симуляційної транзакції (щоб підписники бачили вже узгоджений стан у БД).

`LobbyEventsListener` зараз робить структуровані **`Logger`**-повідомлення — заготовка під метрики чи WS.

Фраза: *«Події доменного рівня, не технічні; еміт після успіху, для battle — після commit TX.»*

## 6. Версіонування API

### Концепція

- **Версія в URL** (`/api/v1/...`) — зрозуміло для клієнтів і проксі.
- **Не перейшли** на офіційне `app.enableVersioning` Nest (щоб не робити синхронно breaking для Lambda/Swagger/фронту).
- **Еволюція контракту JSON** усередині v1 через поле **`schemaVersion`** у payload (приклад: `simulationResult` у лобі з `schemaVersion: 2` для мультиплеєру).

Це описано в **`src/common/api-versioning.ts`** і в тексті опису Swagger.

Фраза: *«Breaking HTTP — через новий префікс або окрему узгоджену міграцію versioning; точкові зміни полів — через schemaVersion.»*

## 7. Що НЕ робили (можна обговорити з ментором)

- **Транзакція навколо `submitConfig`** — у плані була як опція (середній пріоритет); за потреби: read з write lock або коротка TX між перевіркою статусу і записом конфігу.
- **Події → WebSocket для клієнта** — поки лише заготовка; фронт і далі через polling/refetch, якщо не додано шлюз.
- **Nest URI versioning** — свідомо відкладено до окремого PR з чеклістом деплою.

## Питання, які доречно поставити менторові

1. Чи достатньо **умовного UPDATE** для join, чи у проді з великою конкуренцією доречніший **pessimistic lock**?
2. Який рівень **ізоляції** транзакцій Postgres потрібен для конкретного навантаження (за замовчуванням звичайно read committed)?
3. Коли є сенс **емітити події синхронно vs через чергу**, якщо з’явиться важкий side-effect?
4. Як у вашій команді прийнято узгоджувати **semver OpenAPI vs URL v1 vs schemaVersion у ресурсах**?
